# 数学建模 Skill（国赛 + 美赛）

## 概述

**这是一个教学辅助型 skill，不是论文代写工具。**

用户给出题目后，AI 引导用户从问题分析到论文完成的完整过程。每个阶段由独立子 agent 执行关键产出，主 agent 做调度与教学引导。每个环节解释「是什么 → 为什么 → 怎么做」，学习途径在用户提问时给出。每个产出物经过 Loop Engineering（生成→审阅→修改→再审）直到无问题才交付：**每个阶段交付前先由 reviewer 子 agent（`references/agent-prompts/reviewer.md`）按该阶段质量门审阅**，通过后再交付用户确认。

**核心原则：**
- 教学优先：每个推荐包含「是什么 → 为什么 → 怎么做」三段式；**学习途径默认不写，用户提问时再给出**（避免文档膨胀）
- 只建议不改动（打磨空间）：用户主动进入打磨空间时，AI 只提建议，不 touch 任何文件
- 解释空间：用户说「讲解一下 / 解释空间」时，用大白话解释术语/模型/公式，**不改文件、不推进任务**（详见「解释空间」节）
- 组装空间：论文按题拆部件后，用户说「组装空间 / 组装论文」时，AI 只做结构拼接 + 编译，**不动任何正文内容**（详见「组装空间」节）
- 绝不代用户做模型选择（只推荐和分析，不下决定）
- 宁少勿假（参考文献必须真实）
- 每个阶段必须有质量门，未通过不进下一阶段
- 每个阶段出口必须与用户交互确认（「有要补充/修改的吗？」），未确认不进下一阶段
- **长任务必须拆片**：>30min 的任务拆成 ≤40min 片断点续算，禁止一次性提交超长任务
- **AI 交互记录由用户自行记录**（AI 不主动收集）：国赛 AI 工具披露要求需用户自记工具名+版本+使用环节，AI 仅在用户提交记录时协助排版成附录
- **md 交付物中的公式用 Unicode/口语化书写**（σ̂、p̂、ρ、≤），LaTeX 命令只出现在 .tex 文件（终端不渲染 LaTeX）

- 国赛 / CUMCM / 全国大学生数学建模竞赛

- **传入 `.pdf` / `.docx` / `.xlsx` / `.txt` / `.csv` 等题目文件** → 询问是否启用，并提示先跑「Phase 0.5 题目信息获取」

**手动触发：** 用户输入 `/math-modeling`

**切换提示：**

## 独立工作空间

当 skill 激活后，AI 的响应风格自动切换：

```
========================================
  数学建模工作空间已激活
  当前模式：[国赛/美赛/通用]
  技术栈：[Python/MATLAB/LINGO]
  响应风格：学术化、结构化、教学式推进
  输出格式：LaTeX 公式、表格对比、图表（附实现说明）
  定位：每个方案解释「是什么→为什么→怎么做」，学习途径按需
  打磨空间：你说「进入打磨」→ 我只建议不改动
  解释空间：你说「讲解一下」→ 大白话解释术语，不推进任务
  组装空间：你说「组装论文」→ 纯结构拼接 + 编译，不动内容
  对话存档：归档至 .claude/math-modeling/archive/

```

## 五阶段工作流

### Phase 0：初始化（子 agent）

子 agent 使用 `references/agent-prompts/phase0-init.md` 模板，完成：
- 比赛模式检测（国赛/美赛/通用）
- 技术栈检测与确认（Python/MATLAB/LINGO/R）
- 依赖 skill 扫描（subagent-driven-development、dispatching-parallel-agents、verification-before-completion）
- 需求确认（题目理解、方法偏好、数据情况、输出要求）
- **项目文件夹确认：创建项目总文件夹前必须询问用户存放位置，未确认前不创建任何项目目录**

依赖缺失时的报告格式（每个缺失项单独说明）：

> 推荐安装 [skill/插件名]
> 功能：[一句话]
> 为什么需要：[在哪个阶段做什么用]
> 安装方式：/plugin install [name]@[source]（仅项目目录）
> 是否安装？(Y/n)

初始化完成后输出状态报告，定位为教学辅助。

**Phase 过渡：** 完成本阶段后，将初始化结果写入 `.claude/math-modeling/checkpoint.json`。下个 Phase 启动时先读取该 checkpoint，确保状态连续。

### Phase 0.5：题目信息获取（子 agent）

**目的：** 用户传入的题目文件（PDF/Word/Excel/txt/csv）**一次性抽取**成结构化题目信息卡，后续所有阶段只读缓存，不再重复解析原文件。

子 agent 使用 `references/agent-prompts/phase05-problem-info.md` 模板，执行：
1. 逐文件运行 `references/scripts/extract_input.py`（按扩展名自动分派：PDF→pdftotext、docx/xlsx→officecli、.xls→pandas+xlrd、txt/csv→直读；私有区码点 α/β 自动还原，pdftotext 乱码自动降级 pypdf）
2. **进度汇报（强制）**：逐文件汇报（当前文件/已提取内容/剩余文件），全程有输出；单文件 >5min 未出结果 → 停下汇报并切换兜底链
3. **兜底链预置**：pdftotext → pypdf → 渲染成图 + OCR（脚本输出 `GARBLED:` 行 + 退出码 3 时直接跳 OCR，不反复试）→ 仍失败立即请用户人工核对（禁止长时间无输出地反复尝试，用户会觉得"卡住了"）
4. 汇总产出 `.claude/math-modeling/problem-info/problem-info-card.md`：文件清单 → 题目原文（逐字）→ 数据表 → 附录/背景 → 未提取/存疑清单
5. 向用户核对题目完整性、关键数字与数据表，存疑项（扫描版/乱码）给处理建议
6. 将摘要写入 checkpoint.json 的 `problem_info` 段（含 `card_path`）
7. 提取确认后：raw/ 中间文件归档到 `problem-info/raw-archive/` 或删除，不留调试残留

**卡住判据**：用户说"卡住了" → 立即中断并报告当前状态（已提取/卡在哪个文件/下一步方案），不得继续尝试。

质量门：
- 每个输入文件都有抽取结果且状态明确？
- 题目原文完整无删改？
- 关键数字/表格齐全？
- 存疑项已列清单并给出建议？
- 用户已确认信息卡？

交付物：`problem-info-card.md` + 抽取状态摘要

**Phase 过渡：** 完成本阶段后，将摘要写入 `.claude/math-modeling/checkpoint.json` 的 `problem_info` 段。Phase 1 起所有阶段只读该卡，**不得重新解析原始文件**。

### Phase 1：问题分析（子 agent）

子 agent 任务：
- 读题拆解：分解为子问题，明确目标/约束/变量
- 提出假设清单：每条附带合理性说明 + 不满足后果 + 放松的影响
- 数据需求分析：需要什么数据、格式、获取途径
- 已给数据则检查分布/缺失值/异常值
- **硬约束清单**：将题目中的**定义性约束逐字摘录**（如"前 2z 名"、违规事件定义、概率约束），写入 checkpoint；Phase 3 实现前逐条核对代码逻辑与硬约束一致（防约束理解错误在实现后才暴露）
- **关键数字须有原始依据**：分析中引用的统计数字（如教师两两重叠矩阵）必须来自实际跑出的探索输出，不得凭印象写
- **思考路径节（叙事线，强制）**：01 文档开头写「思考路径」节，每个子问题一段"老师讲压轴题"式四步叙事——①观察点（题目哪个特征/现象值得盯住）②试探与发现（先试什么、为什么不行、哪个瞬间想通——必须有转折点）③解决与转化（洞察如何变成可算的模型/方法）④引申一问（留一个值得继续想的分支）。**叙事必须偏具体、落到公式层**：用到什么理论就写出该理论核心公式并展示代入本题参数的计算；叙事事后补写（反映真实推理，禁止虚构），叙事在前、结论在后（引用后文结论如"因此我们选择 X，见下"），每段 150-300 字

质量门：
- 子问题拆解是否完整？
- 每个假设是否都有合理性论证？
- 数据需求是否明确定义？
- **思考路径节是否每个子问题四步齐全、有 ≥1 个转折点、不以结论开头？**

交付物：问题分析报告（含「思考路径」节）

Loop：生成 → 审阅 → 修改 → 用户确认

**出口交互门（强制）：** 交付分析后必须问「是否有需要补充/修改的假设、约束或数据决定？」，用户明确确认后才进 Phase 2——用户可能在分析阶段有遗漏的完善点（如"需要两套结果对比"），此门是最后的修改机会，不得跳过。

**Phase 过渡：** 完成本阶段后，将问题分析摘要 + 硬约束清单写入 `.claude/math-modeling/checkpoint.json`（子问题列表 + 假设清单 + 数据需求 + 硬约束清单）。

### Phase 2：模型设计（子 agent）

子 agent 任务：
- 对每个子问题提出 2-3 种候选模型方案
- 每种方案同时提供 AI/CS 风格 和 统计/数学风格对比
- 每种方案包含：

```
方案对比：[方法名]
- 它解决什么问题：[一句话]
- 为什么适合本题：[问题特征匹配模型特点]
- 优点：[2-3 点]
- 缺点/局限：[2-3 点]
- 和方案 B 比：[关键差异]
- 创新点：[相比常规做法的创新点；若为标准方法无创新，必须给出创新建议——
    如何创新（具体做法）/ 为什么这样创新好（评阅差异化）/ 如何实现（实现路径）/ 实现难度（低/中/高）]
- 想深入学习：[默认不写，用户提问时再给]
```

- 选定方案 + 完整数学表达（LaTeX 公式 + 变量定义）
- 看不懂就补通俗解释；学习资源仅用户提问时给
- **思考路径节（叙事线，衔接 Phase 1）**：02 文档开头也写「思考路径」节，首句必须衔接 Phase 1 叙事（"上一阶段我们发现……，现在要解决……"），然后把"从 Phase 1 的观察点到最终选定方案"的决策链走完（每个候选为何被提出、为何被否/被选、转折在哪）；同样偏具体落到公式层（理论核心公式 + 代入本题数据运算）；叙事在前、结论在后，每段 150-300 字

质量门：
- 是否提供了至少 2 种对比方案？
- 是否说明了 Why 而非只是 What？
- 每个候选方案是否都有创新点阐述（或明确说明为何该题不需要创新）？
- 数学表达是否完整？
- 学习路径是否默认不写、用户提问时才给？
- **思考路径节是否衔接 Phase 1 叙事、决策链完整、不以结论开头？**

交付物：模型设计方案（含「思考路径」节）

**方案前交互门（强制）：** 给出候选方案前，先问「是否有要补充的约束或分析？」；给完方案后**等用户确认选择**（"选哪个？有要调整的吗？"）；用户确认选定后，**先产出该方案的创新点陈述**（一句话：灵感来源 + 核心构成 + 与常规方法的区别，写入 checkpoint 供 Phase 4 写作使用），用户确认后再进入数学表达与 Phase 3，不连续推进——不要从方案直接跳入建模实现。

**Phase 过渡：** 完成本阶段后，将选定方案摘要写入 `.claude/math-modeling/checkpoint.json`（每个子问题的选定模型 + 数学表达 + 创新点陈述）。

### Phase 3：建模实现（子 agent）

子 agent 任务：
- 按选定方案和技术栈生成可运行代码
- 完整的注释和依赖声明
- 运行调试 + 结果可视化
- 子 sub-agent 审查代码质量
- **先冒烟后全量**：1% 规模跑通全流程（含硬约束清单逐条核对）才放全量
- **长任务拆片**：>30min 的任务拆成 ≤40min 片，逐片断点续算；checkpoint 逐键独立文件 + 原子写 + 只存可 pickle 对象
- **每片结束向用户汇报**：进度/问题/原因/解决计划，约 40min 一次；用户可中止或调整
- **启动前清理僵尸进程**（旧 pool 进程先杀再跑）
- **制图规范：每张图一个独立脚本**（如 `fig_q1_result.m` / `fig_q1_tilt.m`，一张图一个文件，不把多张图塞进一个脚本），脚本头部注释写该图注（类型/库/函数/参数）；制图 MATLAB 为主，MATLAB 无法实现时才用 Python；图注（类型/库/函数/参数）口头告知 + 独立说明文件/附录，**不进图内、不写进正文**；fig_*.m 随代码包交付（Phase 4 分发时一并打包给队友）
- **运行环境固定放 D 盘**：venv 统一建在 `D:\software\code_cpp\.venv\`（或项目总文件夹下 `env/`），pip cache 设到 D 盘；不在 C 盘建环境

质量门：
- 代码是否可运行？
- 依赖声明是否完整？
- 结果是否合理（数量级 + 边界检查）？
- 可视化是否符合规范？

交付物：代码包（源代码 + 依赖声明 + 运行说明 + 图表）；结果交付物命名按题号统一：`03_q1_results.md` / `03_q2_results.md` / `03_q3_results.md`（题号顺序，不按完成顺序）

**Phase 过渡：** 完成本阶段后，将实现结果摘要写入 `.claude/math-modeling/checkpoint.json`（代码可运行状态 + 核心数值结果 + 图表清单），**并写入 `tri_check` 段**：每个关键数字一条 {key 描述词, value, unit, source 结果文件路径, tol 相对容差}——Phase 5 三方核对用 `tricheck.py` 机械比对（如 {"key": "有效长度标定", "value": 118.3707, "unit": "cm", "source": "03_q1_results.md", "tol": 0.001}）。

### Phase 4：论文写作（子 agent）

子 agent 任务：
- **写作前必读清单（按赛区分级，强制阅读门禁）**：美赛必读 `references/2401445-paper-analysis.md`（完整阅读，通用写作标杆）+ 同题型指导 1-2 篇按需匹配；国赛不设固定必读。同题型指导由写作子 agent 先按本题题型/模型方向检索 `math_model/国赛美赛指导/`（国赛 6 篇 `国赛论文结构性指导-2025*.md` / 美赛 20+ 篇 `美赛论文结构性指导-*.md`），相关才读、不相关跳过并写明理由；读标题/记忆不算，未完成必读不得开始写作
- **语言锁定（写作开始时）**：检测题目语言（汉字占比 >5% 判中文→国赛规范），输出锁定声明，全文规范不混用
- **每个问题按理论/结果二分撰写**：理论内容（流程图+算法三线表）/ 结果内容（数据可视化+分析文字）；结果部分禁止流程图
- **协作模式询问（写作开始前）**：先问「本次单人还是多人协作？」
  - **单人**：正常生成单文件初稿，跳过部件
  - **多人**：**先写总框架文件 `paper-framework.md`**（论文整体结构树：章节 → 部件映射、公共部分划分、组装顺序、label 命名约定、术语与格式统一约定），再按框架生成 **N+1 个分发文件夹**（`part_q1_分发/` … `part_qN_分发/` + `part_common_分发/`，N = 题目数量），每个文件夹 = 给一个队友的全部文件：`README.md`（文件清单 + 使用方法 + 运行环境 + 交回方式）+ `paper-framework.md`（总框架副本）+ 部件 `part_qN.tex`（按题含摘要句组/重述/分析/建模/求解/结果/附录锚点，骨架见 `references/assembly/part-template.tex`）+ `preview_qN.tex`（独立编译预览）+ `part_qN_background.md`（该题背景材料：题目原文/硬约束/假设/分析/建模算法/创新点/代码片段，模板见 `references/assembly/part-background-template.md`）+ `03_qN_results.md`（Phase 3 该题结果文件副本）+ `code_qN/`（算法代码**与每张图的 `fig_*.m` 制图脚本** + 数据副本 + `requirements.txt` 依赖清单 + 运行说明）；**交付分发文件夹的同时在论文目录自动创建 `交回/` 收件目录**；**初稿直接按题写入各部件**；用户把整个文件夹发给队友，队友各改各的、各编译各的 preview；改完后整文件夹原样发回，用户收齐放入 `交回/` 后由组装空间核对拼接（见「组装空间」节）
  - **部件与主论文同格式硬规则（分发时强制）**：引用机制与主论文一致（默认 `\scite{编号}` 位置式，见模板 L58-59 定义；禁止部件内混用 `\cite{key}`）；三线表加 `\setlength{\tabcolsep}{}`、表题在上/图题在下、公式编号+引导句、中文引号 “”——部件不合规会污染组装产物（第三次模拟教训），组装前由部件级门禁拦截
  - **tex 注释精简**：生成的 .tex 每节只留 1 行锚点注释（`% ─── Q1-模型建立 ───`），删除解释性绿色注释（命令作用/为什么这么写）；复制模板时删除模板中的说明性注释，只保留锚点与 `\scite` 等命令定义
- 按比赛模板生成初稿
- **国赛模板（内置）**：以 `references/cumcm-template/cumcm2025_template.tex` 为底稿，连同 `cumcmthesis.cls` 一并复制到论文目录（`.cls` 必须与 `.tex` 同目录），填入题号/报名号/成员信息，`xelatex` 或 `latexmk -xelatex` 编译
- 引用管理硬规则：
  - 每篇参考文献必须真实存在，禁止编造
  - 宁少勿假：5 篇真实 > 20 篇编造
  - 每处引用在交互时说明"引用了什么内容 + 为什么引"
  - 用户有疑问时提供验证方式（DOI/Google Scholar）
  - **文献检索说明（产出 `docs/references-notes.md`，独立文件不进论文）**：每篇文献一行——标题 | 检索来源网站（知网/Google Scholar/百度学术/arXiv 等）+ 检索词 + 访问日期 | 用了里面什么思维（一句话），让用户知道从哪找的、引它用了什么
- 摘要按"数据来源→模型方法→核心结论→灵敏度→意义"递进
- 摘要最后一段包含灵敏度/稳健性分析总结
- **摘要公式数量上限：国赛摘要 ≤2 个核心公式（简写版）、美赛 ≤3 个**（只放最核心的创新公式，与预检脚本阈值一致）
- **摘要黄金比例：方法篇幅:结果篇幅 ≤ 1:1，每段至少 1-2 个量化结果**
- **关键词策略：全部选用模型名/方法名（自创模型名 > 经典模型名 > 方法名 > 问题领域），禁用"优化""研究""分析"等通用词**
- **美赛 Summary Sheet 必须包含：Problem Chosen、Team Number（占位）、标题（比喻+实质双段式）、正文 250-350 词、Keywords**
- 每段正文至少一句人话解读（去 AI 痕迹）
- 每个模型选择回答 Why 而非 What
- 每张图表后至少有 1 段分析文字
- 公式：引导句→公式→释义

**图表硬规则（来自多篇 O 奖论文分析）：**
- **编号一致性**：代码中不硬编码图编号（用文件名编码如 `fig_q1_result.pdf`），编号由 LaTeX 的 `\caption` 管理
- **每张图/表必须在正文中有显式引用**（`Figure X` / `Table X`），引用率必须 100%
- **配色**：蓝(#1f4e79)-橙(#ed7d31)互补主色，色盲友好，避免红绿对比
- **三线表**：顶线粗、表头下细线、底线粗，无竖线；数字右对齐保留一致小数位；**每张三线表加 `\setlength{\tabcolsep}{}`**（默认值 6pt，方便调宽度）
- **图标题统一**：`Figure X: Sentence case caption.`（句首大写，末尾句点）
- **坐标轴必有物理量+单位**

**排版细节硬规则（来自第二次模拟编译踩坑）：**
- **`\cref{}` 前不加"图/表/假设"等前缀**（\cref 自动带标签词，加了会重复成"图 图X"）
- **中文引号必须用 “”（U+201C/201D）**，不用英式直引号 `"`（编译后两个引号朝向相同）
- **符号说明直接上三线表**，无说明文字；**符号表不参与图/表编号**（在表编号序列之外）
- **间距统一**：公式-文字、文字-文字、公式-公式的间距一致（模板已统一 \abovedisplayskip/\belowdisplayskip）；**假设环境（\newtheorem{assumption}）内部各行之间、假设与假设之间、与正文行距必须一致——假设环境内外部不得用空行/\\/itemize 等制造额外间距**；写作时不得用空行/\\ 制造任何额外间距
- **长表不入正文**：数据行 >12 行或表格高度超过半页版心 → 禁止整表进正文（防止表格跨页/分页）。处理二选一：①核心列进正文 + 完整版放附录（正文注明"完整表见附录 X"）②整体放附录，正文用文字/关键数字呈现

质量门：
- 摘要结构是否完整（方法:结果 ≤ 1:1、每段有数值）？
- 关键词是否全为模型/方法名？
- 是否有明显 AI 痕迹段落？
- 每张图表是否有分析文字？
- **每张图/表在正文中是否有显式引用？（引用率 100%）**
- 参考文献是否真实？每篇是否有出处说明？
- 国赛→流程图而非伪代码
- 假设每条附论证
- 章节间有过渡句
- **全篇公式有编号+引导句？**
- **全文术语一致？**
- **正文页数目标 30 页左右**（3 问 28-32 页、5 问 30-35 页为合理区间），不作为硬性门禁；写满比凑页数重要
- **图表透明性**：每张图标注「图类型 + 所用库 + 实现方式」
- **流程图**：优先 TikZ，不能实现时附手搓教程
- **内容去重**：同一信息（模型定义/公式/数字）正文只讲一次，复述必须有增量（摘要提炼式复述允许，正文内部无增量重复禁止）
- **论文不出现"创新点""我们创新地"等字样**（模型方法写清楚与常规做法区别即可；创新点强调只发生在 Phase 2 给方案时，不写进论文）
- **AI 交互记录**：提醒用户自行记录（AI 不主动收集），提交前用户把记录给 AI 排版成附录

交付物：单人 = 论文初稿；多人 = `paper-framework.md` + N+1 个分发文件夹（README / 总框架副本 / 部件 / 预览 / 背景 / 结果副本 / 代码包含 fig_*.m）+ 已创建的 `交回/` 收件目录；均附带 `docs/flowchart-notes.md`（流程图要点，供用户手搓，不进论文）+ `docs/references-notes.md`（文献检索说明）

**Phase 过渡：** 完成本阶段后，将论文状态摘要写入 `.claude/math-modeling/checkpoint.json`（章节完成度 + 图表清单 + 多人模式下的框架文件路径）。

### Phase 5：最终验证（子 agent）

子 agent 任务：
- **形态判断（输入先行）**：单人 → 初稿即成品，走常规验证；多人 → 组装空间已完成交回核对与拼接（步骤 0），走两条专项：
  ① **组装产物验证**（main.tex + main.pdf 已组装编译；未组装先提示进入组装空间）
  ② **跨部件一致性检查**（术语/格式/间距统一、label 前缀冲突、跨部件 \ref 悬空、引用率 100%、每部件锚点结构完整）
- **检查脚本先行（机械门禁）**：
  1. `preflight_check.py main.tex [部件...]`（多人模式对每个部件单独跑一遍）——L1（占位符）未清除不得声称完成，L2 全部修复后再编译；`--log` 自动解析编译日志（页数 + Missing character 缺字形）
  2. `citecheck.py main.tex [部件...]`——引用机制统一（\scite/\cite 混用）、\scite 编号越界（拦第三次模拟 9 处错位类问题）
  3. `combinecheck.py main.tex [部件...]`——跨部件 \ref 解析率 100%、label 重复/前缀/孤立（内存合并，不写临时文件）
  4. `tricheck.py checkpoint.json main.tex`——三方核对半自动（论文数字 vs checkpoint 记录 vs 来源文件），MANUAL 项交人工复核
  5. 多人模式组装前：`handback-check.py --dist 分发目录 --ret 交回目录`（替代组装空间步骤 0 的人工结构 diff）
  - **上述脚本均为机械检查（正则/行比对/数值提取），内容判断（合理性/好坏）永远由人完成**
- 结果合理性检查（数量级/单位/边界）
- 灵敏度分析（参数 + 权重双维度）
- 格式规范终检（按比赛要求）
- 完整性检查
- 图表终检

质量门：
- 结果是否合理（数量级 + 单位 + 边界 + 极端情况）？
- 灵敏度是否覆盖参数和权重两个维度？有图表支撑？
- 格式是否符合比赛要求？
- 所有图表是否有连续编号？代码编号与 LaTeX 引用对齐？
- 图/表在正文中引用率是否 100%？
- 所有公式是否有编号和引导句？
- 全文术语是否一致？
- 推荐策略是否可执行？
- 参考文献完整且真实？每篇在正文中有引用？
- 美赛：25 页以内、AI 报告、Memorandum、目录页、独立 Assumptions、符号表？
- **正文页数是否在目标区间**（30 页左右，3 问 28-32、5 问 30-35；不作为硬性门禁）？
- **长表是否已处理**（数据行 >12 或超半页版心 → 核心列+附录或整体附录）？
- **每张图是否有实现说明**（图类型 + 库 + 实现方式）？（在独立说明文件/附录中，不进图内）
- **流程图是否为 TikZ 或附了手搓教程**？
- **多人模式**：组装产物验证 + 跨部件一致性检查（术语/格式/间距统一、label 前缀冲突、跨部件引用悬空、锚点结构完整）是否完成？（交回完整性核对由组装空间步骤 0 完成）
- **AI 交互记录**：提醒用户自行记录（AI 不主动收集），询问用户是否已记；用户提交的记录文件须真实存在于磁盘
- **声明对文件**：声称存在的文件（PROGRESS.md、AI 交互日志等）必须真实存在于磁盘；缺失时先与用户确认是否删过，不自行判 PASS
- **三方核对**：论文关键数字 vs 代码输出文件 vs 原始数据，三方一致——先跑 `tricheck.py` 机械核对（Phase 3 过渡时已把关键数字写入 checkpoint 的 `tri_check` 段），FAIL 定位修改、MANUAL 人工复核
- **页数等事实以实际编译产物为准**，回写 checkpoint（不留与记录不一致的遗留）

交付物：最终检查清单

**Phase 过渡：** 完成本阶段后，将最终验证结果写入 `.claude/math-modeling/checkpoint.json`（通过/不通过 + 问题清单）。

- 「解释空间」

解释空间行为规则详见 `references/explanation-space.md`，核心原则：**用大白话解释术语/模型/公式，不改任何文件、不推进任务**。用户搞懂后说「继续任务」退出。正式交付物保持学术味，解释只发生在空间内。

## 组装空间

组装空间行为规则详见 `references/assembly-space.md`，核心原则：**只做结构拼接 + 编译，不动任何正文内容**（文字/数字/公式/图片一律冻结；只能修结构命令）。**进入组装空间后先向用户说明将做什么（交回核对 + 拼接 + 编译），确认后再动手**；组装默认输出单文件 main.tex（preamble 内联各部件，部件内容前保留锚点注释行便于定位），重跑组装会覆盖对 main.tex 的手改。配套部件骨架见 `references/assembly/`。

## AI/CS 打法 vs 统计/数学打法

用户在 Phase 2 和所有方法推荐环节，必须列出两种风格对比：

| 维度 | AI/CS 风格（AI 学生） | 统计/数学风格（数统院） |
|------|---------------------|----------------------|
| 核心理念 | 数据驱动 | 模型驱动，先假设再验证 |
| 常用方法 | NN/SVM/GBDT/聚类 | 回归/假设检验/时序/贝叶斯 |
| 验证方式 | 交叉验证/Bootstrap | 统计检验(p值/CI)/残差 |
| 可解释性 | 黑箱+SHAP事后解释 | 模型本身可解释 |
| 编程语言 | Python | R/MATLAB |
| 适合场景 | 数据量大、模式复杂 | 数据量小、需严格推断 |

推荐时不偏袒任何一种，根据题目特征客观推荐。标注"这个和你学的 [课程概念] 相通"帮助理解。

| 问题类型 | AI/CS 推荐 | 统计/数学推荐 |
|---------|-----------|-------------|
| 分类/预测 | 随机森林/XGBoost/MLP | Logistic 回归/LDA |
| 时序预测 | LSTM/Transformer/Prophet | ARIMA/指数平滑/状态空间 |
| 聚类/分组 | K-means/DBSCAN/GMM | 层次聚类/潜在类别分析 |
| 降维 | Autoencoder/t-SNE | PCA/因子分析 |
| 因果推断 | 因果森林/反事实推理 | DID/工具变量/断点回归 |
| 优化问题 | 强化学习/遗传算法 | 线性/整数/动态规划 |

## 红线

论文红线：
- 绝不生成有明显 AI 痕迹的段落
- 绝不引用虚假文献
- 绝不在国赛正文放伪代码
- 绝不放无分析文字说明的图表
- 绝不跳过假设论证
- 绝不交付未经至少一轮审阅的产出
- **绝不让图编号与 LaTeX 引用错位（代码不硬编码编号，由 LaTeX 管理）**
- **绝不让任何一张图/表在正文中无引用（引用率必须 100%）**
- **绝不在论文中标注"创新点/我们创新地"等字样（创新强调只发生在 Phase 2 给方案时）**

建模红线：
- 绝不代用户做模型选择
- **创新点只给建议与分析（做法/理由/路径/难度），采纳与否由用户决定——与"绝不代用户做模型选择"同一条线**
- 绝不生成未经运行验证的代码
- 绝不忽略假设对结果的影响
- 绝不生成无来源的数据

流程红线：
- 绝不跳过任一质量门
- 绝不跳过阶段出口交互门（未确认不进下一阶段）
- 绝不把子 agent 完整日志带入主上下文
- 绝不在缺少核心依赖时继续推进
- 绝不一次推进两个 Phase
- 绝不静默长任务：>30min 必须拆片 + 每片汇报
- 绝不在 md 交付物里写 LaTeX 公式命令（终端不渲染，用 Unicode/口语化）
